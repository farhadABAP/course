CRITICAL Automated Grading

Your submission is graded automatically — not by a human. This means:

  • Naming is decisive. If a task specifies an exact object name, use exactly that name.
  • Case sensitivity matters. ADT is case-sensitive for identifiers.
  • Types and visibilities must be exact. PUBLIC, PROTECTED, PRIVATE — as specified.
  • There are no partial points for "almost right".
Mental shift: This exam tests familiarity, not clever algorithms. Those who have already created the object types in ADT have an advantage. Theory alone is not enough.

Allowed vs. Forbidden in ABAP Cloud

The Restricted Language Version blocks many classic statements. This is a central exam topic — also in practical tasks (the syntax checker reports forbidden constructs).

✓ Allowed
  • Released SAP APIs (C1 contract)
  • CDS View Entities
  • ABAP SQL with released tables/views
  • ABAP OO (classes, interfaces)
  • RAP Business Objects
  • ADT-based development
  • ABAP Unit tests
  • Released BAdIs
  • Custom CDS entities
✗ Forbidden
  • Direct SELECT on non-released tables
  • CALL FUNCTION to non-released FMs
  • Classic Dynpro / SAP GUI screens
  • Classic lists / SAPscript / Smart Forms
  • Modifications to SAP standard
  • EXEC SQL / Native SQL
  • Obsolete statements (e.g. TABLES)
  • Direct access to SAP internals
  • FORM / PERFORM (subroutines)

Released APIs — Why They Matter

A Released API is an SAP object with a released contract (C1 for SAP-internal use, C0 for external). Only released APIs are stable across releases — that is why the cloud development model restricts you to them.

Exam tip: The syntax checker in ADT flags forbidden statements immediately. If you use a classic statement that is not allowed during the exam, you will get an error message. Trust the checker.

⌨️ Modern ABAP

Core ABAP

Modern Expressions — Exam-Relevant

In practical tasks you will use modern ABAP syntax. The syntax checker helps, but you should know the basic forms.

Inline Declaration



" Instead of: DATA lv_name TYPE string.
DATA(lv_name) = |Farhad|.

LOOP AT lt_customers INTO DATA(ls_customer).
    DATA(lv_text) = |Customer: { ls_customer-name }|.
ENDLOOP.

VALUE Operator



" Fill internal table
DATA(lt_numbers) = VALUE int4_table(
    ( 10 )
    ( 20 )
    ( 30 )
).

" Fill structure
DATA(ls_customer) = VALUE ty_customer(
    id     = 100
    name   = 'Acme'
    status = 'NEW'
).

COND / SWITCH



DATA(lv_category) = COND string(
    WHEN lv_amount > 1000 THEN 'HIGH'
    WHEN lv_amount > 100  THEN 'MEDIUM'
    ELSE 'LOW'
).

DATA(lv_name) = SWITCH string( lv_code
    WHEN 'A' THEN 'Alpha'
    WHEN 'B' THEN 'Beta'
    ELSE 'Unknown'
).

FOR Expression



" Extract names
DATA(lt_names) = VALUE string_table(
    FOR ls IN lt_customers
    ( ls-name )
).

" With WHERE filter
DATA(lt_active) = VALUE string_table(
    FOR ls IN lt_customers
        WHERE ( status = 'A' )
    ( ls-name )
).

REDUCE



" Calculate sum
DATA(lv_total) = REDUCE decfloat34(
    INIT sum = 0
    FOR ls IN lt_items
    NEXT sum = sum + ls-amount
).

FILTER



" Filter table
DATA(lt_active) = FILTER #(
    lt_customers
    WHERE status = 'A'
).

CORRESPONDING



" Map structures
DATA(ls_target) = CORRESPONDING ty_target(
    ls_source
).

" Map internal tables
DATA(lt_target) = CORRESPONDING ty_target_table(
    lt_source
).

String Template



DATA(lv_text) = |Customer { lv_id } has status { lv_status }.|.

" Formatting
DATA(lv_amt) = |Total: { lv_amount NUMBER = USER } EUR|.

" Date
DATA(lv_date) = |Created: { lv_created DATE = USER }|.

Table Expression



" Single row — throws if not found
DATA(ls_customer) = lt_customers[ id = 100 ].

" Safe with default
DATA(ls_customer2) = VALUE #(
    lt_customers[ id = 999 ]
    DEFAULT VALUE #( )
).
Exam tip: You do not have to write modern syntax from memory. The syntax checker in ADT shows errors immediately. Start typing and let it guide you. But you should be able to recognize the constructs.

📦 Modularization

Core ABAP

Three Classic Techniques

Technique Purpose Cloud-Ready?
Subroutine (FORM/PERFORM) Legacy procedural modularization No — obsolete in cloud
Function Module (FUNCTION) Reusable function Only if released (RFC)
Method (METHOD) Preferred OO modularization Yes

Methods — The Modern Way

  • Defined in classes (global or local)
  • Importing / Exporting / Changing / Returning parameters
  • Can raise class-based exceptions
  • Instance or static methods
  • Encapsulation via visibility sections

Method Example



CLASS zcl_calc DEFINITION.
    PUBLIC SECTION.
        METHODS add
            IMPORTING
                iv_a          TYPE i
                iv_b          TYPE i
            RETURNING
                VALUE(rv_sum) TYPE i.
ENDCLASS.

CLASS zcl_calc IMPLEMENTATION.
    METHOD add.
        rv_sum = iv_a + iv_b.
    ENDMETHOD.
ENDCLASS.

" Call
DATA(lo_calc) = NEW zcl_calc( ).
DATA(lv_result) = lo_calc->add(
    iv_a = 10
    iv_b = 20
).

Function Modules — When They Still Matter

Function modules are allowed in ABAP Cloud only when they are released (for example, released RFC-enabled function modules). In exam tasks about legacy vs. modern code they are discussed.

Subroutines — Obsolete

FORM / PERFORM are not available in ABAP for Cloud Development. If a task offers a subroutine as the "modern" answer, that is a trap.

Exam tip: A task might require refactoring legacy code. The correct direction is almost always: subroutine → method, global mutable state → encapsulated class, TABLES → typed parameters.

📋 Internal Tables

Core ABAP

Three Table Types

Type Access Key Best for
STANDARD TABLE Index + linear search Non-unique (default) Sequential processing, small tables
SORTED TABLE Binary search on key Unique or non-unique Frequent key reads, sorted output
HASHED TABLE Hash — O(1) Always unique Large tables, frequent key lookups

Primary vs. Secondary Key

A primary key is defined at the table type level and governs uniqueness/sorting. A secondary key can be added later to speed up specific access patterns on the same table. 



" Standard table with secondary key
DATA lt_customers TYPE STANDARD TABLE OF ty_customer
    WITH NON-UNIQUE SORTED KEY by_name
        COMPONENTS name.

" Fast lookup using secondary key
READ TABLE lt_customers
    WITH TABLE KEY by_name
        COMPONENTS name = 'ACME'
    ASSIGNING FIELD-SYMBOL().

Common Operations



" APPEND (standard tables only)
APPEND ls_customer TO lt_customers.

" INSERT
INSERT ls_customer INTO TABLE lt_customers.

" READ TABLE
READ TABLE lt_customers
    INTO DATA(ls_found)
    WITH KEY id = 100.

" LOOP AT with WHERE
LOOP AT lt_customers INTO DATA(ls_c)
    WHERE status = 'A'.
    " ...
ENDLOOP.

" SORT
SORT lt_customers BY name ASCENDING.

" DELETE
DELETE lt_customers WHERE status = 'X'.

" MODIFY
MODIFY lt_customers FROM ls_customer
    TRANSPORTING name.

Performance Rules

  • READ TABLE on a standard table with WITH KEY is linear — slow for large tables.
  • READ TABLE ... INDEX is O(1) on any table type.
  • Use ASSIGNING + field symbols to avoid copying large rows in loops.
  • Prefer HASHED for large lookup tables, SORTED when you also need order.
  • Avoid LOOP AT ... WHERE on huge tables when a filtered SQL read would be faster.
Exam tip: "Which table type is fastest for key access?" — HASHED. "Which is fastest for index access?" — STANDARD (every type is O(1) on index, but standard is designed for it).

📖 ABAP Dictionary (DDIC)

Core ABAP

Core DDIC Objects

Object Purpose Reuse
Domain Technical definition: type, length, value range Reusable across data elements
Data Element Semantic meaning: field labels, documentation Used in structures and tables
Structure Reusable field group, no data storage Components for tables and programs
Table Physical storage (transparent tables) Defined with data elements

Table Categories

  • Transparent tables — one-to-one with database tables; the standard choice.
  • Pooled tables — grouped into a database pool; historical, limited in cloud.
  • Cluster tables — multiple tables stored in one cluster; historical, limited in cloud.

Technical Settings

  • Data class — affects physical placement.
  • Size category — expected row count.
  • Buffering — full, generic, or none; cached at application server level.
  • Logging — whether changes are logged.

Field Length Change & Activation

If you shorten a table field, the system may need to convert data and the table cannot be converted online — the conversion is performed during activation. This is a classic exam topic because it affects availability.

Buffering Notes



" Buffered access
SELECT SINGLE * FROM zconfig
    INTO @DATA(ls_cfg)
    WHERE key_field = @lv_key.

Buffered tables are read from the application server buffer, not the database. This is fast for small, rarely-changing configuration data — and dangerous for frequently-changing data.

Exam tip: A task might present a table that is read constantly but changes often. Buffering would be wrong because the buffer would become stale. Choose buffering for read-mostly configuration tables only.

Calling Syntax — Heavily Tested



" Static method call (class =>)
DATA(lv_result) = zcl_util=>get_version( ).

" Instance method call (->)
DATA(lo_obj) = NEW zcl_util( ).
DATA(lv_name) = lo_obj->get_name( ).

" Static attribute access
DATA(lv_count) = zcl_util=>mv_counter.

" Instance attribute access
DATA(lv_id) = lo_obj->mv_id.

Memorize the two arrows: => is for static access, -> is for instance access. A very common exam trap swaps them.

Interface Example



INTERFACE zif_customer.
    METHODS get_name
        RETURNING VALUE(rv_name) TYPE string.
ENDINTERFACE.


CLASS zcl_customer DEFINITION.
    PUBLIC SECTION.
        INTERFACES zif_customer.
ENDCLASS.


CLASS zcl_customer IMPLEMENTATION.
    METHOD zif_customer~get_name.
        rv_name = 'ACME'.
    ENDMETHOD.
ENDCLASS.


" Polymorphic call
DATA lo_cust TYPE REF TO zif_customer.
lo_cust = NEW zcl_customer( ).
DATA(lv_name) = lo_cust->get_name( ).

Inheritance & Redefinition



CLASS zcl_base DEFINITION.
    PUBLIC SECTION.
        METHODS describe
            RETURNING VALUE(rv) TYPE string.
ENDCLASS.

CLASS zcl_child DEFINITION
    INHERITING FROM zcl_base.
    PUBLIC SECTION.
        METHODS describe REDEFINITION.
ENDCLASS.

Exception Classes

  • CX_STATIC_CHECK — must be declared or handled
  • CX_DYNAMIC_CHECK — checked at runtime
  • CX_NO_CHECK — not checked


" Declare static check exception
METHODS do_work
    RAISING zcx_my_error.

" Raise
RAISE EXCEPTION TYPE zcx_my_error
    EXPORTING
        textid = zcx_my_error=>invalid_input.

Visibilities — Exam-Relevant

A typical exam task requires a class hierarchy with exact visibility rules:

  • PUBLIC — accessible from anywhere
  • PROTECTED — only in the class and subclasses
  • PRIVATE — only in the class itself
  • PUBLIC READ-ONLY — readable from outside, writable only internally
Exam tip: In the practical exam, visibility is graded automatically. If the task says "attribute X should be public-readonly", then it must be defined exactly that way — not public, not private.

🗄️ ABAP SQL & Code Pushdown

≤ 10%

Core Topics

  • SELECT / JOIN / WHERE
  • GROUP BY / HAVING / ORDER BY
  • Aggregations
  • SQL expressions & functions
  • Host variables (@)
  • Database-side processing
  • Code pushdown

Modern SELECT



SELECT FROM zcustomer
       FIELDS id,
              name,
              status
       WHERE status = @lv_status
       INTO TABLE @DATA(lt_customers).

Joins



SELECT FROM zcustomer AS c
    INNER JOIN zcompany AS co
        ON c~company_id = co~company_id
    FIELDS c~id,
           c~name,
           co~company_name
    WHERE c~status = @lv_status
    INTO TABLE @DATA(lt_result).

Aggregation & GROUP BY



SELECT FROM zorders
    FIELDS customer_id,
           COUNT(*) AS order_count,
           SUM( amount ) AS total_amount
    GROUP BY customer_id
    HAVING SUM( amount ) > @lv_min
    ORDER BY total_amount DESCENDING
    INTO TABLE @DATA(lt_totals).

SQL Expressions



" CASE, CAST, COALESCE, string functions
SELECT FROM zcustomer
    FIELDS id,
           name,
           CASE WHEN status = 'A'
                THEN 'Active'
                ELSE 'Inactive'
           END AS status_text,
           COALESCE( phone, 'N/A' ) AS phone
    INTO TABLE @DATA(lt_result).

Code Pushdown

Code pushdown means moving data-intensive processing as close to the database as possible instead of retrieving large datasets and processing everything in ABAP.

✓ Push down
  • Filtering (WHERE)
  • Joining related tables
  • Aggregation (SUM, COUNT)
  • Sorting (ORDER BY)
  • Column projection (only needed fields)
  • Calculations in SQL expressions
✗ Keep in ABAP
  • Complex procedural logic with side effects
  • Business rules with external calls
  • Row-by-row formatting for UI
  • Logic that cannot be expressed in SQL
Exam tip: A task might present a slow report. The correct answer is almost always to reduce data transfer and push processing down — not to add buffering or increase memory.

🐞 Debugging & Performance

Core ABAP

Tools You Must Know

Tool Transaction Purpose
ABAP Debugger /h Step through running code
ABAP Profiler SAT Aggregated runtime analysis of ABAP execution
SQL Trace ST05 Analyze database access, find slow SQL
Code Inspector SCI Static checks: performance, security, syntax
ABAP Test Cockpit ATC Central quality gate for transports

ABAP Profiler (SAT)

  • Aggregated view: total time per procedure
  • Hit list: most expensive operations
  • Call hierarchy: who called what
  • Database access breakdown

SQL Trace (ST05)

  • Captures all database statements during a trace
  • Identifies full table scans and missing indexes
  • Shows the execution plan
  • Look for SELECT * where a narrower projection would suffice
  • Look for SELECT inside LOOP (classic performance killer)

Classic Anti-Patterns



" ❌ SELECT inside LOOP — N+1 queries
LOOP AT lt_customers INTO DATA(ls_c).
    SELECT SINGLE name FROM zcompany
        INTO @DATA(lv_name)
        WHERE company_id = @ls_c-company_id.
ENDLOOP.

" ✓ One JOIN or one SELECT ... FOR ALL ENTRIES
SELECT c~id, co~name
    FROM zcustomer AS c
    INNER JOIN zcompany AS co
        ON c~company_id = co~company_id
    INTO TABLE @DATA(lt_result).

Other Performance Principles

  • Select only the columns you need — avoid SELECT *.
  • Use WHERE, not ABAP filtering, when possible.
  • Use FOR ALL ENTRIES carefully — always guard against an empty driver table.
  • Prefer ASSIGNING to INTO in loops for large rows.
  • Avoid nested loops when a hashed lookup works.
Exam tip: In the practical exam, you can use the ABAP Debugger and the syntax checker to verify your code. Test what you built — with IF_OO_ADT_CLASSRUN and MAIN.

📊 CDS Data Modeling

21–30%

CDS View Entity



@EndUserText.label: 'Customer'

define view entity ZI_Customer
    as select from zcustomer
{
    key id,
        name,
        status,
        created_by
}

Association



define view entity ZI_Customer
    as select from zcustomer

    association [0..1]
        to I_CompanyCode as _CompanyCode
        on $projection.CompanyCode =
           _CompanyCode.CompanyCode
{
    key id,
        CompanyCode,
        _CompanyCode
}

Cardinality



" [0..1]  = at most one
" [1..1]  = exactly one
" [0..*]  = any number
" [1..*]  = at least one

association [0..*]
    to I_OrderItem as _Items
    on $projection.OrderId = _Items.OrderId

Path Expression



_CompanyCode.CompanyName as CompanyName

Parameters



define view entity ZI_CustomerByStatus
    with parameters
        p_status : abap.char(1)
    as select from zcustomer
{
    key id,
        name,
        status
}
where status = $parameters.p_status

Key Concepts

  • Association vs. JOIN — an association is a lazy, reusable relationship definition; a JOIN is eager and executed in the query.
  • Cardinality — declared on the association, used by consumers (e.g. RAP) to understand the relationship.
  • Path Expression — navigate from one entity to another via _Association.Field.
  • Annotations — @EndUserText.label, @Semantics, @AccessControl, @ObjectModel — drive UI and behavior.
  • Parameters — input values bound at query time via $parameters.
Exam tip: A task might require generating a CDS view from a table and extending it with associations. Practice generating in ADT — the wizard guides you.

Managed vs. Unmanaged

Managed
  • Framework handles CREATE/UPDATE/DELETE
  • Persistent table declared in BDEF
  • You add determinations, validations, actions
  • Default choice for new BOs
Unmanaged
  • You implement save/read logic yourself
  • Used when persistence is non-standard
  • Often wraps legacy APIs or external data
  • More code, more control

⚙️ RAP Behavior Definition

RAP

Managed Behavior



managed implementation in class
    zbp_i_customer unique;

strict ( 2 );

define behavior for ZI_Customer
persistent table zcustomer
lock master
authorization master
{
    create;
    update;
    delete;

    field ( readonly ) id;

    determination setStatus
        on modify { create; }

    validation checkName
        on save { create; update; }

    action approve result [1] $self;
}

Determination

Automatically derives or changes values based on business events. Triggered by framework events (on modify, on save).

Validation

Checks whether business data is valid before saving. Reports messages; does not change data.

Action

Represents an explicit business operation initiated by a consumer or application. Called via EML or OData.

Feature Control



" Static instance-level control
field ( readonly ) id, created_at, created_by;

" Dynamic control via feature instance
" in the implementation
" (e.g. disable delete for certain instances)
Very important: Do not confuse determination, validation and action.
  • Determination — derives/changes values
  • Validation — checks and reports
  • Action — explicit consumer-triggered operation

⚡ Entity Manipulation Language

RAP

CREATE



MODIFY ENTITIES OF ZI_Customer
    IN LOCAL MODE

    ENTITY Customer

    CREATE FIELDS
        ( name status )

    WITH VALUE #(
        (
            %cid   = 'C1'
            name   = 'Test'
            status = 'NEW'
        )
    )

    MAPPED DATA(lt_mapped)
    FAILED DATA(lt_failed)
    REPORTED DATA(lt_reported).

READ



READ ENTITIES OF ZI_Customer
    IN LOCAL MODE

    ENTITY Customer
    ALL FIELDS WITH VALUE #(
        (
            id = 100
        )
    )

    RESULT DATA(lt_result)
    FAILED DATA(lt_failed)
    REPORTED DATA(lt_reported).

COMMIT



COMMIT ENTITIES
    RESPONSE OF ZI_Customer
    FAILED   DATA(lt_failed)
    REPORTED DATA(lt_reported).

EML Concepts

  • READ ENTITIES / MODIFY ENTITIES
  • CREATE / UPDATE / DELETE
  • %cid — client-side temporary ID for new rows
  • MAPPED / FAILED / REPORTED
  • COMMIT ENTITIES
  • IN LOCAL MODE — bypasses authorization, used inside behavior implementations

EML vs. ABAP SQL

Aspect EML ABAP SQL
Works on RAP business objects Database tables / CDS
Triggers behavior Yes (determinations, validations, actions) No
Authorization Yes (unless LOCAL MODE) Handled separately
Transactional buffer Yes — commit needed Direct DB write (restricted in cloud)
Exam tip: A task might require creating a business object instance with all validations and determinations applied. The answer is EML, not direct SQL.

Service Binding

The service binding connects the service definition to a protocol and runtime used to expose the service. Common binding types:

  • OData V2 — UI (Fiori) usage
  • OData V4 — UI (Fiori) usage, modern
  • Web API — machine-to-machine
  • SQL — direct SQL access via CDS
  • InA — analytics

Know the Difference

Artifact Question

Fiori Elements Relationship

Fiori elements apps consume OData services exposed via service bindings. Annotations in the CDS model (@UI, @ObjectModel) drive the generated UI.

Common confusion: Service definition and service binding are not the same artifact.
  • Definition — what
  • Binding — how

Why Clean Core?

The Clean Core approach aims to keep the SAP core stable and upgradeable while placing extensions in appropriate supported extension mechanisms.

Three Extension Models

Model Where Tools Use for
In-app Inside S/4HANA Cloud Key user tools, custom fields, custom logic Small configuration-level extensions by key users
Developer Inside S/4HANA Cloud ABAP Cloud, ADT, RAP, released APIs Full ABAP extensions, BAdIs, RAP BOs
Side-by-side SAP BTP ABAP Environment ABAP Cloud on BTP New apps, integrations, extensions

Important Concepts

  • Released APIs (C0, C1 contracts)
  • Extension points
  • Upgrade stability
  • ABAP Cloud
  • Custom CDS entities
  • Released BAdIs
  • No modifications to SAP standard
Exam thinking: When several extension approaches are possible, consider whether the solution follows supported extension mechanisms and Clean Core principles. A modification to standard SAP code is almost never the right answer.

4 Implement the Behavior Pool 



CLASS lhc_CustomerLab DEFINITION
    INHERITING FROM cl_abap_behavior_handler.

    PRIVATE SECTION.
        METHODS setDefaults FOR DETERMINE
            ON MODIFY IMPORTING keys FOR CustomerLab.

        METHODS checkName FOR VALIDATE
            ON SAVE IMPORTING keys FOR CustomerLab.

        METHODS approve FOR MODIFY
            IMPORTING keys FOR ACTION CustomerLab~approve
            RESULT result.
ENDCLASS.

CLASS lhc_CustomerLab IMPLEMENTATION.

    METHOD setDefaults.
        MODIFY ENTITIES OF ZI_CustomerLab IN LOCAL MODE
            ENTITY CustomerLab
            UPDATE FIELDS ( status created_by created_at )
            WITH VALUE #(
                FOR key IN keys (
                    %tky       = key-%tky
                    status     = 'NEW'
                    created_by = sy-uname
                    created_at = utclong_current( )
                )
            ).
    ENDMETHOD.

    METHOD checkName.
        READ ENTITIES OF ZI_CustomerLab IN LOCAL MODE
            ENTITY CustomerLab
            FIELDS ( name ) WITH VALUE #(
                FOR key IN keys ( %tky = key-%tky )
            )
            RESULT DATA(lt_cust).

        LOOP AT lt_cust INTO DATA(ls_cust).
            IF ls_cust-name IS INITIAL.
                APPEND VALUE #(
                    %tky = ls_cust-%tky
                ) TO failed-CustomerLab.

                APPEND VALUE #(
                    %tky = ls_cust-%tky
                    %msg = new_message_with_text(
                        severity = if_abap_behv_message=>severity-error
                        text     = 'Name must not be empty'
                    )
                ) TO reported-CustomerLab.
            ENDIF.
        ENDLOOP.
    ENDMETHOD.

    METHOD approve.
        MODIFY ENTITIES OF ZI_CustomerLab IN LOCAL MODE
            ENTITY CustomerLab
            UPDATE FIELDS ( status )
            WITH VALUE #(
                FOR key IN keys (
                    %tky   = key-%tky
                    status = 'APPROVED'
                )
            ).

        READ ENTITIES OF ZI_CustomerLab IN LOCAL MODE
            ENTITY CustomerLab
            ALL FIELDS WITH VALUE #(
                FOR key IN keys ( %tky = key-%tky )
            )
            RESULT DATA(lt_result).

        result = VALUE #(
            FOR ls IN lt_result (
                %tky   = ls-%tky
                %param = ls
            )
        ).
    ENDMETHOD.

ENDCLASS.

A2 — Internal table optimization

" Declaration: replace STANDARD with HASHED

DATA lt_customers TYPE HASHED TABLE OF ty_cust
    WITH UNIQUE KEY id.

" Optimized loop — no nested loop

LOOP AT lt_ids INTO DATA(lv_id).

    DATA(ls_customer) = VALUE ty_cust(
        lt_customers[ id = lv_id ]
        DEFAULT VALUE #( )
    ).

    IF ls_customer IS NOT INITIAL.
        " process
    ENDIF.

ENDLOOP.
Why this is correct:
  • HASHED TABLE with UNIQUE KEY gives O(1) lookup by id.
  • The table expression lt_customers[ id = lv_id ] is the modern replacement for READ TABLE.
  • Wrapping in VALUE ty_cust( ... DEFAULT VALUE #( ) ) avoids an exception if the row is missing — the empty structure is returned.
  • Nested loops eliminated — big performance win for large data sets.
A3 — ABAP SQL with code pushdown

CLASS zcl_mock_report DEFINITION
    PUBLIC
    CREATE PUBLIC.

    PUBLIC SECTION.
        TYPES: BEGIN OF ty_result,
                   customer_id  TYPE zorder_mock-customer_id,
                   order_count  TYPE i,
                   total_amount TYPE decfloat34,
               END OF ty_result.

        TYPES ty_result_table TYPE STANDARD TABLE OF ty_result
            WITH EMPTY KEY.

        DATA mt_result TYPE ty_result_table READ-ONLY.

        METHODS run
            IMPORTING iv_min_amount TYPE decfloat34.

ENDCLASS.

CLASS zcl_mock_report IMPLEMENTATION.

    METHOD run.
        SELECT FROM zorder_mock
            FIELDS customer_id,
                   COUNT(*) AS order_count,
                   SUM( amount ) AS total_amount
            GROUP BY customer_id
            HAVING SUM( amount ) > @iv_min_amount
            ORDER BY total_amount DESCENDING
            INTO TABLE @mt_result.
    ENDMETHOD.

ENDCLASS.
Why this is correct:
  • All aggregation (COUNT, SUM) happens on the database — this is code pushdown.
  • Filtering with HAVING avoids transferring unneeded rows.
  • Sorting is done with ORDER BY in the SQL, not in ABAP.
  • No SELECT * — only the required columns are selected.

" ───────── CDS View Entity: ZR_MOCK_CUSTOMER ─────────

" ───────── Behavior Definition: ZR_MOCK_CUSTOMER ─────────

managed implementation in class
    zbp_r_mock_customer unique;

strict ( 2 );

define behavior for ZR_Mock_Customer
persistent table zcustomer_mock
lock master
authorization master ( instance )
{
    create;
    update;
    delete;

    field ( readonly ) customer_id, created_by, created_at;

    determination setCreatedInfo
        on modify { create; }

    validation checkNameNotEmpty
        on save { create; update; }
}


" ───────── Behavior Pool: ZBP_R_MOCK_CUSTOMER ─────────

CLASS lhc_ZR_Mock_Customer DEFINITION
    INHERITING FROM cl_abap_behavior_handler.

    PRIVATE SECTION.
        METHODS setCreatedInfo FOR DETERMINE
            ON MODIFY IMPORTING keys FOR ZR_Mock_Customer.

        METHODS checkNameNotEmpty FOR VALIDATE
            ON SAVE IMPORTING keys FOR ZR_Mock_Customer.

ENDCLASS.

CLASS lhc_ZR_Mock_Customer IMPLEMENTATION.

    METHOD setCreatedInfo.
        MODIFY ENTITIES OF ZR_Mock_Customer IN LOCAL MODE
            ENTITY ZR_Mock_Customer
            UPDATE FIELDS ( created_by created_at )
            WITH VALUE #(
                FOR key IN keys (
                    %tky       = key-%tky
                    created_by = sy-uname
                    created_at = utclong_current( )
                )
            ).
    ENDMETHOD.

    METHOD checkNameNotEmpty.
        READ ENTITIES OF ZR_Mock_Customer IN LOCAL MODE
            ENTITY ZR_Mock_Customer
            FIELDS ( name ) WITH VALUE #(
                FOR key IN keys ( %tky = key-%tky )
            )
            RESULT DATA(lt_cust).

        LOOP AT lt_cust INTO DATA(ls_cust).
            IF ls_cust-name IS INITIAL.
                APPEND VALUE #(
                    %tky = ls_cust-%tky
                ) TO failed-ZR_Mock_Customer.

                APPEND VALUE #(
                    %tky = ls_cust-%tky
                    %msg = new_message_with_text(
                        severity = if_abap_behv_message=>severity-error
                        text     = 'Name must not be empty'
                    )
                ) TO reported-ZR_Mock_Customer.
            ENDIF.
        ENDLOOP.
    ENDMETHOD.

ENDCLASS.
Why this is correct:
  • define root view entity marks this as the root of the business object — required for a RAP BO.
  • managed implementation in class ... unique — managed means the framework handles the transactional buffer and persistence.
  • determination setCreatedInfo on modify { create; } — fires on every CREATE operation, before the record is saved.
  • validation checkNameNotEmpty on save { create; update; } — fires when the record is saved, for both create and update.
  • Determinations change data (here: created_by, created_at); validations check data and report messages.
  • In the behavior implementation, IN LOCAL MODE bypasses authorization — this is standard inside behavior pools since authorization was already handled at the outer boundary.
  • The loop iterates through all affected instances and reports a message per invalid row.

Bonus Solution
D1 — Action with result parameter

" ───────── BDEF addition ─────────

action upgradeToPremium result [1] $self;


" ───────── Behavior Pool addition ─────────

METHODS upgradeToPremium FOR MODIFY
    IMPORTING keys FOR ACTION ZR_Mock_Customer~upgradeToPremium
    RESULT result.

METHOD upgradeToPremium.

    " Update status
    MODIFY ENTITIES OF ZR_Mock_Customer IN LOCAL MODE
        ENTITY ZR_Mock_Customer
        UPDATE FIELDS ( status )
        WITH VALUE #(
            FOR key IN keys (
                %tky   = key-%tky
                status = 'PREMIUM'
            )
        ).

    " Read the updated rows back
    READ ENTITIES OF ZR_Mock_Customer IN LOCAL MODE
        ENTITY ZR_Mock_Customer
        ALL FIELDS WITH VALUE #(
            FOR key IN keys ( %tky = key-%tky )
        )
        RESULT DATA(lt_result).

    " Populate result parameter
    result = VALUE #(
        FOR ls IN lt_result (
            %tky   = ls-%tky
            %param = ls
        )
    ).

ENDMETHOD.


" ───────── EML test class ─────────

CLASS zcl_mock_action_test DEFINITION
    PUBLIC
    FINAL
    CREATE PUBLIC.

    PUBLIC SECTION.
        INTERFACES if_oo_adt_classrun.
ENDCLASS.

CLASS zcl_mock_action_test IMPLEMENTATION.

    METHOD if_oo_adt_classrun~main.

        " Create
        MODIFY ENTITIES OF ZR_Mock_Customer
            ENTITY ZR_Mock_Customer
            CREATE FIELDS ( customer_id name country )
            WITH VALUE #(
                ( %cid        = 'C1'
                  customer_id = '999'
                  name        = 'Test Customer'
                  country     = 'DE' )
            )
            MAPPED DATA(lt_mapped).

        COMMIT ENTITIES.

        " Call action
        MODIFY ENTITIES OF ZR_Mock_Customer
            ENTITY ZR_Mock_Customer
            EXECUTE upgradeToPremium
            FROM VALUE #(
                ( %key-customer_id = '999' )
            )
            RESULT DATA(lt_result).

        COMMIT ENTITIES.

        " Output result
        LOOP AT lt_result INTO DATA(ls_result).
            out->write( |Customer { ls_result-%param-customer_id } |
                     && | now { ls_result-%param-status }| ).
        ENDLOOP.

    ENDMETHOD.

ENDCLASS.
Why this is correct:
  • action upgradeToPremium result [1] $self declares the action with a cardinality of one result per instance, returning the self entity type.
  • The MODIFY ENTITIES ... UPDATE inside the action changes the status.
  • The READ ENTITIES ... ALL FIELDS retrieves the up-to-date row so we can return it to the caller via result.
  • The result parameter is populated with %tky (the technical key of each instance) and %param (the actual data structure).
  • In the EML test, COMMIT ENTITIES is required after CREATE and after the action to persist changes to the database.
  • IF_OO_ADT_CLASSRUN is the modern way to runnable-test a console class in ADT — much easier than creating a report.

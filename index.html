KRITISCH Automatisierte Bewertung

Ihre Abgabe wird automatisiert bewertet — nicht von einem Menschen. Das bedeutet:

  • Benennung ist entscheidend. Wenn eine Aufgabe einen exakten Objektnamen vorgibt, verwenden Sie genau diesen.
  • Groß-/Kleinschreibung beachten. ADT ist case-sensitiv bei Bezeichnern.
  • Typen und Sichtbarkeiten exakt einhalten. PUBLIC, PROTECTED, PRIVATE — wie vorgegeben.
  • Es gibt keine Teilpunkte für "fast richtig".
Mentaler Shift: Diese Prüfung testet Familiarität, nicht clevere Algorithmen. Wer die Objekttypen in ADT schon einmal angelegt hat, ist im Vorteil. Theorie allein reicht nicht.

Erlaubt vs. Verboten in ABAP Cloud

Die Restricted Language Version blockiert viele klassische Statements. Dies ist ein zentrales Prüfungsthema — auch in praktischen Aufgaben (der Syntax-Checker meldet verbotene Konstrukte).

✓ Erlaubt
  • Released SAP APIs (C1 Contract)
  • CDS View Entities
  • ABAP SQL mit released Tables/Views
  • ABAP OO (Klassen, Interfaces)
  • RAP Business Objects
  • ADT-basierte Entwicklung
  • ABAP Unit Tests
  • Released BAdIs
  • Custom CDS Entities
✗ Verboten
  • Direct SELECT auf nicht-released Tables
  • CALL FUNCTION auf nicht-released FMs
  • Classic Dynpro / SAP GUI Screens
  • Classic Lists / SAPscript / Smart Forms
  • Modifikationen am SAP-Standard
  • EXEC SQL / Native SQL
  • Obsolete Statements (z.B. TABLES)
  • Direkter Zugriff auf SAP-Interna
  • FORM / PERFORM (Subroutines)

Released APIs — Warum sie wichtig sind

Eine Released API ist ein SAP-Objekt mit einem Released Contract (C1 für SAP-interne Nutzung, C0 für externe). Nur Released APIs sind über Releases hinweg stabil — deshalb beschränkt das Cloud-Entwicklungsmodell darauf.

Prüfungstipp: Der Syntax-Checker in ADT markiert verbotene Statements sofort. Wenn Sie in der Prüfung ein klassisches Statement verwenden, das nicht erlaubt ist, erhalten Sie eine Fehlermeldung. Vertrauen Sie auf den Checker.

Moderne Ausdrücke — Prüfungsrelevant

In praktischen Aufgaben werden Sie moderne ABAP-Syntax verwenden. Der Syntax-Checker hilft, aber Sie sollten die Grundformen kennen.

Inline Declaration



" Statt: DATA lv_name TYPE string.
DATA(lv_name) = |Farhad|.

LOOP AT lt_customers INTO DATA(ls_customer).
    DATA(lv_text) = |Customer: { ls_customer-name }|.
ENDLOOP.

VALUE Operator



" Interne Tabelle füllen
DATA(lt_numbers) = VALUE int4_table(
    ( 10 )
    ( 20 )
    ( 30 )
).

" Struktur füllen
DATA(ls_customer) = VALUE ty_customer(
    id     = 100
    name   = 'Acme'
    status = 'NEW'
).

COND / SWITCH



DATA(lv_category) = COND string(
    WHEN lv_amount > 1000 THEN 'HIGH'
    WHEN lv_amount > 100  THEN 'MEDIUM'
    ELSE 'LOW'
).

DATA(lv_name) = SWITCH string( lv_code
    WHEN 'A' THEN 'Alpha'
    WHEN 'B' THEN 'Beta'
    ELSE 'Unknown'
).

FOR Expression



" Namen extrahieren
DATA(lt_names) = VALUE string_table(
    FOR ls IN lt_customers
    ( ls-name )
).

" Mit WHERE-Filter
DATA(lt_active) = VALUE string_table(
    FOR ls IN lt_customers
        WHERE ( status = 'A' )
    ( ls-name )
).

REDUCE



" Summe berechnen
DATA(lv_total) = REDUCE decfloat34(
    INIT sum = 0
    FOR ls IN lt_items
    NEXT sum = sum + ls-amount
).

FILTER



" Tabelle filtern
DATA(lt_active) = FILTER #(
    lt_customers
    WHERE status = 'A'
).

CORRESPONDING



" Strukturen mappen
DATA(ls_target) = CORRESPONDING ty_target(
    ls_source
).

" Interne Tabelle mappen
DATA(lt_target) = CORRESPONDING ty_target_table(
    lt_source
).

String Template



DATA(lv_text) = |Customer { lv_id } has status { lv_status }.|.

" Formatierung
DATA(lv_amt) = |Total: { lv_amount NUMBER = USER } EUR|.

" Datum
DATA(lv_date) = |Created: { lv_created DATE = USER }|.

Table Expression



" Einzelner Satz — Exception wenn nicht gefunden
DATA(ls_customer) = lt_customers[ id = 100 ].

" Sicher mit Default
DATA(ls_customer2) = VALUE #(
    lt_customers[ id = 999 ]
    DEFAULT VALUE #( )
).
Prüfungstipp: Sie müssen moderne Syntax nicht auswendig schreiben. Der Syntax-Checker in ADT zeigt Fehler sofort an. Beginnen Sie zu tippen und lassen Sie sich führen. Aber erkennen sollten Sie die Konstrukte.

📦 Modularisierung

Core ABAP

Drei klassische Techniken

Technik Zweck Cloud-Ready?
Subroutine (FORM/PERFORM) Legacy-prozedurale Modularisierung Nein — obsolet in Cloud
Funktionsbaustein (FUNCTION) Wiederverwendbare Funktion Nur wenn released (RFC)
Methode (METHOD) Bevorzugte OO-Modularisierung Ja

Methoden — Der moderne Weg

  • Definiert in Klassen (global oder lokal)
  • Importing / Exporting / Changing / Returning Parameter
  • Können klassenbasierte Exceptions auslösen
  • Instanz- oder statische Methoden
  • Kapselung über Sichtbarkeitsbereiche

Methoden-Beispiel



CLASS zcl_calc DEFINITION.
    PUBLIC SECTION.
        METHODS add
            IMPORTING
                iv_a          TYPE i
                iv_b          TYPE i
            RETURNING
                VALUE(rv_sum) TYPE i.
ENDCLASS.

CLASS zcl_calc IMPLEMENTATION.
    METHOD add.
        rv_sum = iv_a + iv_b.
    ENDMETHOD.
ENDCLASS.

" Aufruf
DATA(lo_calc) = NEW zcl_calc( ).
DATA(lv_result) = lo_calc->add(
    iv_a = 10
    iv_b = 20
).

Funktionsbausteine — Wann sie noch relevant sind

Funktionsbausteine sind in ABAP Cloud nur erlaubt, wenn sie released sind (z.B. released RFC-enabled Function Modules). In Prüfungsaufgaben zu Legacy-Code vs. modernem Code werden sie thematisiert.

Subroutines — Obsolet

FORM / PERFORM sind in ABAP for Cloud Development nicht verfügbar. Wenn eine Aufgabe eine Subroutine als "moderne" Lösung anbietet, ist das eine Falle.

Prüfungstipp: Eine Aufgabe könnte verlangen, Legacy-Code zu refaktorisieren. Die richtige Richtung ist fast immer: Subroutine → Methode, globaler mutabler Zustand → gekapselte Klasse, TABLES → typisierte Parameter.

📋 Interne Tabellen

Core ABAP

Drei Tabellentypen

Typ Zugriff Schlüssel Am besten für
STANDARD TABLE Index + lineare Suche Non-unique (Default) Sequenzielle Verarbeitung, kleine Tabellen
SORTED TABLE Binäre Suche auf Schlüssel Unique oder non-unique Häufige Schlüssel-Lesezugriffe, sortierte Ausgabe
HASHED TABLE Hash — O(1) Immer unique Große Tabellen, häufige Schlüssel-Lookups

Primärer vs. Sekundärer Schlüssel

Ein Primärschlüssel wird auf Tabellentyp-Ebene definiert und bestimmt Eindeutigkeit/Sortierung. Ein Sekundärschlüssel kann später hinzugefügt werden, um bestimmte Zugriffsmuster auf derselben Tabelle zu beschleunigen. 



" Standardtabelle mit Sekundärschlüssel
DATA lt_customers TYPE STANDARD TABLE OF ty_customer
    WITH NON-UNIQUE SORTED KEY by_name
        COMPONENTS name.

" Schneller Lookup über Sekundärschlüssel
READ TABLE lt_customers
    WITH TABLE KEY by_name
        COMPONENTS name = 'ACME'
    ASSIGNING FIELD-SYMBOL().

Häufige Operationen



" APPEND (nur Standardtabellen)
APPEND ls_customer TO lt_customers.

" INSERT
INSERT ls_customer INTO TABLE lt_customers.

" READ TABLE
READ TABLE lt_customers
    INTO DATA(ls_found)
    WITH KEY id = 100.

" LOOP AT mit WHERE
LOOP AT lt_customers INTO DATA(ls_c)
    WHERE status = 'A'.
    " ...
ENDLOOP.

" SORT
SORT lt_customers BY name ASCENDING.

" DELETE
DELETE lt_customers WHERE status = 'X'.

" MODIFY
MODIFY lt_customers FROM ls_customer
    TRANSPORTING name.

Performance-Regeln

  • READ TABLE auf einer Standardtabelle mit WITH KEY ist linear — langsam bei großen Tabellen.
  • READ TABLE ... INDEX ist O(1) bei jedem Tabellentyp.
  • ASSIGNING + Feldsymbole verwenden, um das Kopieren großer Zeilen in Schleifen zu vermeiden.
  • HASHED für große Lookup-Tabellen bevorzugen, SORTED wenn auch die Reihenfolge benötigt wird.
  • LOOP AT ... WHERE auf riesigen Tabellen vermeiden, wenn ein gefilterter SQL-Read schneller wäre.
Prüfungstipp: "Welcher Tabellentyp ist am schnellsten für Schlüsselzugriff?" — HASHED. "Welcher ist am schnellsten für Indexzugriff?" — STANDARD (jeder Typ ist O(1) auf Index, aber Standard ist dafür ausgelegt).

📖 ABAP Dictionary (DDIC)

Core ABAP

Core DDIC-Objekte

Objekt Zweck Wiederverwendung
Domäne Technische Definition: Typ, Länge, Wertebereich Wiederverwendbar über Datenelemente
Datenelement Semantische Bedeutung: Feldlabels, Dokumentation Verwendet in Strukturen und Tabellen
Struktur Wiederverwendbare Feldgruppe, kein Datenspeicher Komponenten für Tabellen und Programme
Tabelle Physischer Speicher (transparente Tabellen) Definiert mit Datenelementen

Tabellenkategorien

  • Transparente Tabellen — Eins-zu-eins mit Datenbanktabellen; die Standardwahl.
  • Pooled Tables — in einem Datenbankpool gruppiert; historisch, in Cloud eingeschränkt.
  • Cluster Tables — mehrere Tabellen in einem Cluster; historisch, in Cloud eingeschränkt.

Technische Einstellungen

  • Data Class — beeinflusst die physische Platzierung.
  • Size Category — erwartete Zeilenanzahl.
  • Buffering — full, generic oder none; auf Applikationsserver-Ebene gecacht.
  • Logging — ob Änderungen protokolliert werden.

Feldlängenänderung & Aktivierung

Wenn Sie ein Tabellenfeld verkürzen, muss das System möglicherweise Daten konvertieren und die Tabelle kann nicht online konvertiert werden — die Konvertierung wird bei der Aktivierung durchgeführt. Dies ist ein klassisches Prüfungsthema, da es die Verfügbarkeit beeinflusst.

Buffering-Hinweise



" Gepufferter Zugriff
SELECT SINGLE * FROM zconfig
    INTO @DATA(ls_cfg)
    WHERE key_field = @lv_key.

Gepufferte Tabellen werden aus dem Applikationsserver-Puffer gelesen, nicht aus der Datenbank. Dies ist schnell für kleine, sich selten ändernde Konfigurationsdaten — und gefährlich für sich häufig ändernde Daten.

Prüfungstipp: Eine Aufgabe könnte eine Tabelle präsentieren, die ständig gelesen, aber oft geändert wird. Buffering wäre falsch, weil der Puffer veralten würde. Wählen Sie Buffering nur für read-mostly Konfigurationstabellen.

Aufruf-Syntax — Stark getestet



" Statischer Methodenaufruf (Klasse =>)
DATA(lv_result) = zcl_util=>get_version( ).

" Instanzmethodenaufruf (->)
DATA(lo_obj) = NEW zcl_util( ).
DATA(lv_name) = lo_obj->get_name( ).

" Statischer Attributzugriff
DATA(lv_count) = zcl_util=>mv_counter.

" Instanzattributzugriff
DATA(lv_id) = lo_obj->mv_id.

Merken Sie sich die beiden Pfeile: => ist für statischen Zugriff, -> ist für Instanz-Zugriff. Eine sehr häufige Prüfungsfalle vertauscht sie.

Interface-Beispiel



INTERFACE zif_customer.
    METHODS get_name
        RETURNING VALUE(rv_name) TYPE string.
ENDINTERFACE.


CLASS zcl_customer DEFINITION.
    PUBLIC SECTION.
        INTERFACES zif_customer.
ENDCLASS.


CLASS zcl_customer IMPLEMENTATION.
    METHOD zif_customer~get_name.
        rv_name = 'ACME'.
    ENDMETHOD.
ENDCLASS.


" Polymorpher Aufruf
DATA lo_cust TYPE REF TO zif_customer.
lo_cust = NEW zcl_customer( ).
DATA(lv_name) = lo_cust->get_name( ).

Vererbung & Redefinition



CLASS zcl_base DEFINITION.
    PUBLIC SECTION.
        METHODS describe
            RETURNING VALUE(rv) TYPE string.
ENDCLASS.

CLASS zcl_child DEFINITION
    INHERITING FROM zcl_base.
    PUBLIC SECTION.
        METHODS describe REDEFINITION.
ENDCLASS.

Exception-Klassen

  • CX_STATIC_CHECK — muss deklariert oder behandelt werden
  • CX_DYNAMIC_CHECK — wird zur Laufzeit geprüft
  • CX_NO_CHECK — wird nicht geprüft


" Statische Check-Exception deklarieren
METHODS do_work
    RAISING zcx_my_error.

" Auslösen
RAISE EXCEPTION TYPE zcx_my_error
    EXPORTING
        textid = zcx_my_error=>invalid_input.

Sichtbarkeiten — Prüfungsrelevant

Eine typische Prüfungsaufgabe verlangt eine Klassenhierarchie mit exakten Sichtbarkeitsregeln:

  • PUBLIC — von überall zugänglich
  • PROTECTED — nur in der Klasse und Unterklassen
  • PRIVATE — nur in der Klasse selbst
  • PUBLIC READ-ONLY — lesbar von außen, schreibbar nur intern
Prüfungstipp: In der praktischen Prüfung wird die Sichtbarkeit automatisiert geprüft. Wenn die Aufgabe sagt "Attribut X soll public-readonly sein", dann muss es exakt so definiert werden — nicht public, nicht private.

Modernes SELECT



SELECT FROM zcustomer
       FIELDS id,
              name,
              status
       WHERE status = @lv_status
       INTO TABLE @DATA(lt_customers).

Joins



SELECT FROM zcustomer AS c
    INNER JOIN zcompany AS co
        ON c~company_id = co~company_id
    FIELDS c~id,
           c~name,
           co~company_name
    WHERE c~status = @lv_status
    INTO TABLE @DATA(lt_result).

Aggregation & GROUP BY



SELECT FROM zorders
    FIELDS customer_id,
           COUNT(*) AS order_count,
           SUM( amount ) AS total_amount
    GROUP BY customer_id
    HAVING SUM( amount ) > @lv_min
    ORDER BY total_amount DESCENDING
    INTO TABLE @DATA(lt_totals).

SQL-Ausdrücke



" CASE, CAST, COALESCE, String-Funktionen
SELECT FROM zcustomer
    FIELDS id,
           name,
           CASE WHEN status = 'A'
                THEN 'Active'
                ELSE 'Inactive'
           END AS status_text,
           COALESCE( phone, 'N/A' ) AS phone
    INTO TABLE @DATA(lt_result).

Code Pushdown

Code Pushdown bedeutet, datenintensive Verarbeitung so nah wie möglich an die Datenbank zu verlagern, anstatt große Datenmengen abzurufen und alles in ABAP zu verarbeiten.

✓ Push down
  • Filtern (WHERE)
  • Joinen verwandter Tabellen
  • Aggregation (SUM, COUNT)
  • Sortieren (ORDER BY)
  • Spaltenprojektion (nur benötigte Felder)
  • Berechnungen in SQL-Ausdrücken
✗ In ABAP belassen
  • Komplexe prozedurale Logik mit Seiteneffekten
  • Geschäftsregeln mit externen Aufrufen
  • Zeilenweise Formatierung für UI
  • Logik, die nicht in SQL ausgedrückt werden kann
Prüfungstipp: Eine Aufgabe könnte einen langsamen Report präsentieren. Die richtige Antwort ist fast immer, den Datentransfer zu reduzieren und die Verarbeitung nach unten zu verlagern — nicht Buffering hinzuzufügen oder Speicher zu erhöhen.

Core ABAP

Werkzeuge, die Sie kennen müssen

Werkzeug Transaktion Zweck
ABAP Debugger /h Durchlaufenden Code schrittweise ausführen
ABAP Profiler SAT Aggregierte Laufzeitanalyse der ABAP-Ausführung

ABAP Profiler (SAT)

  • Aggregierte Ansicht: Gesamtzeit pro Prozedur
  • Hit List: teuerste Operationen
  • Aufrufhierarchie: wer was aufgerufen hat
  • Datenbankzugriff-Aufschlüsselung

SQL Trace (ST05)

  • Erfasst alle Datenbank-Statements während eines Trace
  • Identifiziert Full Table Scans und fehlende Indizes
  • Zeigt den Ausführungsplan
  • Suchen Sie nach SELECT *, wo eine schmalere Projektion ausreichen würde
  • Suchen Sie nach SELECT innerhalb LOOP (klassischer Performance-Killer)

Klassische Anti-Patterns



" ❌ SELECT innerhalb LOOP — N+1 Queries
LOOP AT lt_customers INTO DATA(ls_c).
    SELECT SINGLE name FROM zcompany
        INTO @DATA(lv_name)
        WHERE company_id = @ls_c-company_id.
ENDLOOP.

" ✓ Ein JOIN oder ein SELECT ... FOR ALL ENTRIES
SELECT c~id, co~name
    FROM zcustomer AS c
    INNER JOIN zcompany AS co
        ON c~company_id = co~company_id
    INTO TABLE @DATA(lt_result).

Weitere Performance-Prinzipien

  • Nur die benötigten Spalten selektieren — SELECT * vermeiden.
  • WHERE verwenden, nicht ABAP-Filterung, wenn möglich.
  • FOR ALL ENTRIES sorgfältig verwenden — immer gegen leere Treibertabelle absichern.
  • ASSIGNING statt INTO in Schleifen bei großen Zeilen bevorzugen.
  • Verschachtelte Schleifen vermeiden, wenn ein Hashed Lookup funktioniert.
Prüfungstipp: In der praktischen Prüfung können Sie den ABAP Debugger und den Syntax-Checker nutzen, um Ihren Code zu verifizieren. Testen Sie, was Sie gebaut haben — mit IF_OO_ADT_CLASSRUN und MAIN.

Wichtige Konzepte

  • Association vs. JOIN — eine Association ist eine lazy, wiederverwendbare Beziehungsdefinition; ein JOIN ist eager und wird in der Query ausgeführt.
  • Kardinalität — auf der Association deklariert, von Konsumenten (z.B. RAP) genutzt, um die Beziehung zu verstehen.
  • Path Expression — Navigation von einer Entity zur anderen über _Association.Field.
  • Annotations — @EndUserText.label, @Semantics, @AccessControl, @ObjectModel — steuern UI und Verhalten.
  • Parameter — Eingabewerte, die zur Query-Zeit über $parameters gebunden werden.

Managed vs. Unmanaged

Managed
  • Framework übernimmt CREATE/UPDATE/DELETE
  • Persistent Table in BDEF deklariert
  • Sie fügen Determinations, Validations, Actions hinzu
  • Standardwahl für neue BOs
Unmanaged
  • Sie implementieren Save/Read-Logik selbst
  • Verwendet, wenn Persistenz nicht standard ist
  • Oft Wrapper um Legacy-APIs oder externe Daten
  • Mehr Code, mehr Kontrolle
Denken Sie in Schichten: CDS beschreibt die Daten. Behavior beschreibt, was passieren kann. Service Definition beschreibt, was exponiert wird. Service Binding macht den Service verfügbar.

⚙️ RAP Behavior Definition

RAP

Managed Behavior



managed implementation in class
    zbp_i_customer unique;

strict ( 2 );

define behavior for ZI_Customer
persistent table zcustomer
lock master
authorization master
{
    create;
    update;
    delete;

    field ( readonly ) id;

    determination setStatus
        on modify { create; }

    validation checkName
        on save { create; update; }

    action approve result [1] $self;
}

Determination

Leitet Werte automatisch ab oder ändert sie basierend auf Geschäftsereignissen. Wird durch Framework-Events ausgelöst (on modify, on save).

Validation

Prüft, ob Geschäftsdaten vor dem Speichern gültig sind. Meldet Nachrichten; ändert keine Daten.

Action

Repräsentiert eine explizite Geschäftsoperation, die von einem Konsumenten oder einer Anwendung initiiert wird. Wird über EML oder OData aufgerufen.

Feature Control



" Statische Instanz-Level-Kontrolle
field ( readonly ) id, created_at, created_by;

" Dynamische Kontrolle über Feature-Instanz
" in der Implementierung
" (z.B. Delete für bestimmte Instanzen deaktivieren)
Sehr wichtig: Verwechseln Sie nicht Determination, Validation und Action.
  • Determination — leitet Werte ab/ändert sie
  • Validation — prüft und meldet
  • Action — explizite, vom Konsumenten ausgelöste Operation

Artefakt Frage

🧹 Clean Core & Erweiterbarkeit

11–20%

Warum Clean Core?

Der Clean-Core-Ansatz zielt darauf ab, den SAP-Kern stabil und upgrade-fähig zu halten, während Erweiterungen in geeignete unterstützte Erweiterungsmechanismen platziert werden.

Drei Erweiterungsmodelle

Modell Wo Werkzeuge Für
In-App In S/4HANA Cloud Key-User-Werkzeuge, Custom Fields, Custom Logic Kleine Konfigurationserweiterungen durch Key-User
Developer In S/4HANA Cloud ABAP Cloud, ADT, RAP, Released APIs Volle ABAP-Erweiterungen, BAdIs, RAP BOs
Side-by-Side SAP BTP ABAP Environment ABAP Cloud auf BTP Neue Apps, Integrationen, Erweiterungen

Wichtige Konzepte

  • Released APIs (C0-, C1-Contracts)
  • Extension Points
  • Upgrade-Stabilität
  • ABAP Cloud
  • Custom CDS Entities
  • Released BAdIs
  • Keine Modifikationen am SAP-Standard
Prüfungsdenken: Wenn mehrere Erweiterungsansätze möglich sind, überlegen Sie, ob die Lösung unterstützte Erweiterungsmechanismen und Clean-Core-Prinzipien befolgt. Eine Modifikation am SAP-Standardcode ist fast nie die richtige Antwort.

Prüfungssimulation
Format: Diese Aufgaben simulieren die praktischen Prüfungsaufgaben. Bearbeiten Sie sie in einer echten ADT-Umgebung. Die Bewertung ist automatisiert — exakte Benennung, Typen und Sichtbarkeiten sind entscheidend.

1 Paket und Transportauftrag anlegen ADT

Szenario: Sie werden in der Prüfung aufgefordert, ein eigenes Paket mit dem korrekten Super-Package und einem Transportauftrag anzulegen. Alle Objekte, die Sie erstellen, müssen in diesem Paket liegen.

  • Transportauftrag zugeordnet
  • Alle Objekte im Paket
Prüfungstipp: Der Paketname und das Super-Package werden exakt vorgegeben. Weichen Sie nicht ab. Der Transportauftrag wird automatisch erstellt, wenn Sie das Paket anlegen.

2 Klassenhierarchie mit exakten Sichtbarkeiten ADT

Szenario: Erstellen Sie eine Klassenhierarchie mit spezifischen Regeln zur Attribut-Sichtbarkeit. Die Aufgabe gibt vor: public-readonly, protected, private — und Sie müssen diese exakt einhalten.
Zu liefern:
  • Oberklasse mit definierten Attributen

  • Sichtbarkeiten exakt wie vorgegeben
  • Methoden ggf. REDEFINITION
Prüfungstipp: Die Sichtbarkeiten werden automatisiert geprüft. PUBLIC READ-ONLY bedeutet: von außen lesbar, nur intern schreibbar. Das ist nicht dasselbe wie PUBLIC.

3 Interne Tabelle optimieren ADT

Szenario: Eine bestehende Implementierung verwendet eine STANDARD TABLE mit linearem READ TABLE in einer Schleife. Optimieren Sie den Code, ohne die Funktionalität zu ändern.
Zu liefern:
  • Optimierte interne Tabelle (HASHED oder SORTED mit Sekundärschlüssel)
  • Angepasste READ-Operation
  • Gleiche Ausgabe
Prüfungstipp: Für unique Key-Lookups ist HASHED die schnellste Wahl. Für sortierte Ausgabe mit Key-Zugriff SORTED.

4 DDIC-Objekte anlegen ADT

Szenario: Erstellen Sie eine transparente Tabelle mit Datenelementen und Domänen. Achten Sie auf die technischen Einstellungen (Data Class, Size Category, Buffering).
Zu liefern:
  • Domäne(n)
  • Datenelement(e)
  • Transparente Tabelle
  • Technische Einstellungen konfiguriert
Prüfungstipp: Die Tabelle muss aktiviert werden. Wenn Feldlängen geändert werden, kann eine Konvertierung nötig sein — bei der Aktivierung.

5 ABAP SQL Query optimieren ADT

Szenario: Ein bestehender Report ruft Daten mit SELECT * ab und filtert in ABAP. Optimieren Sie die Query für Code Pushdown.
Zu liefern:
  • Nur benötigte Spalten selektieren
  • WHERE-Klausel statt ABAP-Filter
  • Aggregation in SQL, falls nötig
  • Ergebnis identisch
Prüfungstipp: Code Pushdown bedeutet: Verarbeitung so nah wie möglich an die Datenbank. SELECT * ist fast immer falsch.

4 Behavior Pool implementieren 



CLASS lhc_CustomerLab DEFINITION
    INHERITING FROM cl_abap_behavior_handler.

    PRIVATE SECTION.
        METHODS setDefaults FOR DETERMINE
            ON MODIFY IMPORTING keys FOR CustomerLab.

        METHODS checkName FOR VALIDATE
            ON SAVE IMPORTING keys FOR CustomerLab.

        METHODS approve FOR MODIFY
            IMPORTING keys FOR ACTION CustomerLab~approve
            RESULT result.
ENDCLASS.

CLASS lhc_CustomerLab IMPLEMENTATION.

    METHOD setDefaults.
        MODIFY ENTITIES OF ZI_CustomerLab IN LOCAL MODE
            ENTITY CustomerLab
            UPDATE FIELDS ( status created_by created_at )
            WITH VALUE #(
                FOR key IN keys (
                    %tky       = key-%tky
                    status     = 'NEW'
                    created_by = sy-uname
                    created_at = utclong_current( )
                )
            ).
    ENDMETHOD.

    METHOD checkName.
        READ ENTITIES OF ZI_CustomerLab IN LOCAL MODE
            ENTITY CustomerLab
            FIELDS ( name ) WITH VALUE #(
                FOR key IN keys ( %tky = key-%tky )
            )
            RESULT DATA(lt_cust).

        LOOP AT lt_cust INTO DATA(ls_cust).
            IF ls_cust-name IS INITIAL.
                APPEND VALUE #(
                    %tky = ls_cust-%tky
                ) TO failed-CustomerLab.

                APPEND VALUE #(
                    %tky = ls_cust-%tky
                    %msg = new_message_with_text(
                        severity = if_abap_behv_message=>severity-error
                        text     = 'Name must not be empty'
                    )
                ) TO reported-CustomerLab.
            ENDIF.
        ENDLOOP.
    ENDMETHOD.

    METHOD approve.
        MODIFY ENTITIES OF ZI_CustomerLab IN LOCAL MODE
            ENTITY CustomerLab
            UPDATE FIELDS ( status )
            WITH VALUE #(
                FOR key IN keys (
                    %tky   = key-%tky
                    status = 'APPROVED'
                )
            ).

        READ ENTITIES OF ZI_CustomerLab IN LOCAL MODE
            ENTITY CustomerLab
            ALL FIELDS WITH VALUE #(
                FOR key IN keys ( %tky = key-%tky )
            )
            RESULT DATA(lt_result).

        result = VALUE #(
            FOR ls IN lt_result (
                %tky   = ls-%tky
                %param = ls
            )
        ).
    ENDMETHOD.

ENDCLASS.

Allowed vs Forbidden in ABAP Cloud

This is the single most tested conceptual distinction. The restricted language version blocks many classic statements. Know which side of the line common features fall on.

✓ Allowed
  • Released SAP APIs (C1 contract)
  • CDS view entities
  • ABAP SQL with released tables/views
  • ABAP OO (classes, interfaces)
  • RAP business objects
  • ADT-based development
  • ABAP Unit tests
  • Released BAdIs
  • Custom CDS entities
✗ Forbidden
  • Direct SELECT on non-released tables
  • CALL FUNCTION to unreleased FMs
  • Classic Dynpro / SAP GUI screens
  • Classic lists / SAPscript / Smart Forms
  • Modifications to SAP standard objects
  • EXEC SQL / native SQL
  • Obsolete statements (e.g. TABLES)
  • Direct access to SAP internals
  • Non-released BAPIs / function modules

Released APIs — Why They Matter

A released API is an SAP object that carries a released contract (C1 for SAP-internal use, C0 for external). Only released APIs are guaranteed to remain stable across releases — that is why the cloud development model restricts you to them.

Exam trap: Do not assume that every classic ABAP statement or direct database access is available in ABAP for Cloud Development. Always ask: "Is this API / statement / object released and allowed in the target development model?"

⌨️ Modern ABAP

Core ABAP

Inline Declaration



DATA(lv_name) = |Farhad|.

LOOP AT lt_customers INTO DATA(ls_customer).

    DATA(lv_text) =
        |Customer: { ls_customer-name }|.

ENDLOOP.

VALUE Operator



DATA(lt_numbers) =
    VALUE int4_table(
        ( 10 )
        ( 20 )
        ( 30 )
    ).

COND / SWITCH



DATA(lv_category) =
    COND string(
        WHEN lv_amount > 1000 THEN 'HIGH'
        WHEN lv_amount > 100  THEN 'MEDIUM'
        ELSE 'LOW'
    ).

DATA(lv_name) =
    SWITCH string( lv_code
        WHEN 'A' THEN 'Alpha'
        WHEN 'B' THEN 'Beta'
        ELSE 'Unknown'
    ).

FOR Expression



DATA(lt_names) =
    VALUE string_table(
        FOR ls IN lt_customers
        ( ls-name )
    ).

" with WHERE
DATA(lt_active) =
    VALUE string_table(
        FOR ls IN lt_customers
            WHERE ( status = 'A' )
        ( ls-name )
    ).

Table Expression



" Single row read — throws if not found
DATA(ls_customer) =
    lt_customers[ id = 100 ].

" Safe read with default
DATA(ls_customer2) =
    VALUE #(
        lt_customers[ id = 999 ]
        DEFAULT VALUE #( )
    ).

String Template



DATA(lv_text) =
    |Customer { lv_id } has status { lv_status }.|.

" Formatting options
DATA(lv_amt) =
    |Total: { lv_amount NUMBER = USER } EUR|.

" Date formatting
DATA(lv_date) =
    |Created: { lv_created DATE = USER }|.
Know the concept: Be able to recognize modern syntax in existing code, not only write it from memory.

📦 Modularization Techniques

Core ABAP

Three Classic Techniques

Technique Purpose Cloud-Ready?
Subroutine (FORM/PERFORM) Legacy procedural modularization No — obsolete in cloud
Function Module (FUNCTION) Reusable remote/local function Only if released (RFC)
Method (METHOD) Preferred OO modularization Yes

Methods — The Modern Way

  • Defined in classes (global or local)
  • Support importing / exporting / changing / returning parameters
  • Can raise class-based exceptions
  • Can be instance or static
  • Enforced encapsulation via visibility sections

Parameter Passing



CLASS zcl_calc DEFINITION.
    PUBLIC SECTION.
        METHODS add
            IMPORTING
                iv_a        TYPE i
                iv_b        TYPE i
            RETURNING
                VALUE(rv_sum) TYPE i.
ENDCLASS.

CLASS zcl_calc IMPLEMENTATION.
    METHOD add.
        rv_sum = iv_a + iv_b.
    ENDMETHOD.
ENDCLASS.

" Call
DATA(lo_calc) = NEW zcl_calc( ).
DATA(lv_result) = lo_calc->add(
    iv_a = 10
    iv_b = 20
).

Function Modules — When They Still Matter

Function modules are allowed in ABAP Cloud only when they are released (for example, released RFC-enabled function modules on the SAP allowlist). You will still see them in classic systems and in exam questions about legacy vs modern code.

Subroutines — Obsolete

FORM / PERFORM are not available in ABAP for Cloud Development. If you see a question offering a subroutine as the "modern" answer, that's a trap.

Exam trap: A question may ask you to refactor legacy procedural code. The correct direction is almost always: subroutine → method, global mutable state → encapsulated class, TABLES → typed parameters.

📋 Internal Tables

Core ABAP

Three Table Types

Type Access Key Best For
STANDARD TABLE Index + linear search Non-unique (default) Sequential processing, small tables
SORTED TABLE Binary search on key Unique or non-unique Frequent key reads, sorted output
HASHED TABLE Hash — O(1) Always unique Large tables, frequent key lookups

Primary vs Secondary Keys

A primary key is defined at table type level and governs uniqueness/sorting. A secondary key can be added later to speed up specific access patterns on the same table. 



" Standard table with secondary key
DATA lt_customers TYPE STANDARD TABLE OF ty_customer
    WITH NON-UNIQUE SORTED KEY by_name
        COMPONENTS name.

" Fast lookup using secondary key
READ TABLE lt_customers
    WITH TABLE KEY by_name
        COMPONENTS name = 'ACME'
    ASSIGNING FIELD-SYMBOL(<ls>).

Common Operations



" APPEND (standard tables only)
APPEND ls_customer TO lt_customers.

" INSERT
INSERT ls_customer INTO TABLE lt_customers.

" READ TABLE
READ TABLE lt_customers
    INTO DATA(ls_found)
    WITH KEY id = 100.

" LOOP AT with WHERE
LOOP AT lt_customers INTO DATA(ls_c)
    WHERE status = 'A'.
    " ...
ENDLOOP.

" SORT
SORT lt_customers BY name ASCENDING.

" DELETE
DELETE lt_customers WHERE status = 'X'.

" MODIFY
MODIFY lt_customers FROM ls_customer
    TRANSPORTING name.

Performance Rules of Thumb

  • READ TABLE on a standard table with WITH KEY is linear — slow for large tables.
  • READ TABLE ... INDEX is O(1) on any table type.
  • Use ASSIGNING + field symbols to avoid copying large rows in loops.
  • Prefer HASHED for large lookup tables, SORTED when you also need order.
  • Avoid LOOP AT ... WHERE on huge tables when a filtered SQL read would be faster.
Exam trap: "Which table type is fastest for key access?" — HASHED. "Which is fastest for index access?" — STANDARD (any type is O(1) on index, but standard is designed for it).

📖 ABAP Dictionary (DDIC)

Core ABAP

Core DDIC Objects

Object Purpose Reuse
Domain Technical definition: type, length, value range Reusable across data elements
Data Element Semantic meaning: field labels, documentation Used in structures and tables
Structure Reusable field group, no data storage Components for tables and programs
Table Physical storage (transparent tables) Defined with data elements

Table Categories

  • Transparent tables — one-to-one with database tables; the standard choice.
  • Pooled tables — grouped into a database pool; historical, limited in cloud.
  • Cluster tables — multiple tables stored in one cluster; historical, limited in cloud.

Technical Settings

  • Data class — affects physical placement.
  • Size category — expected row count.
  • Buffering — full, generic, or none; cached at application server level.
  • Logging — whether changes are logged.

Field Length Change & Activation

If you shorten a table field, the system may need to convert data and the table cannot be converted online — the conversion is performed during activation. This is a classic exam topic because it affects availability.

Buffering Notes



" Buffered access example
SELECT SINGLE * FROM zconfig
    INTO @DATA(ls_cfg)
    WHERE key_field = @lv_key.

Buffered tables are read from the application server buffer, not the database. This is fast for small, rarely-changing configuration data — and dangerous for frequently-changing data.

Exam trap: A question may present a table that is read constantly but changes often. Buffering would be wrong because the buffer would become stale. Choose buffering for read-mostly config tables only.

Calling Syntax — Very Tested



" Static method call (class =>)
DATA(lv_result) = zcl_util=>get_version( ).

" Instance method call (->)
DATA(lo_obj) = NEW zcl_util( ).
DATA(lv_name) = lo_obj->get_name( ).

" Static attribute access
DATA(lv_count) = zcl_util=>mv_counter.

" Instance attribute access
DATA(lv_id) = lo_obj->mv_id.

Memorize the two arrows: => is for static access, -> is for instance access. A very common exam distractor swaps them.

Interface Example



INTERFACE zif_customer.
    METHODS get_name
        RETURNING VALUE(rv_name) TYPE string.
ENDINTERFACE.


CLASS zcl_customer DEFINITION.
    PUBLIC SECTION.
        INTERFACES zif_customer.
ENDCLASS.


CLASS zcl_customer IMPLEMENTATION.
    METHOD zif_customer~get_name.
        rv_name = 'ACME'.
    ENDMETHOD.
ENDCLASS.


" Polymorphic call
DATA lo_cust TYPE REF TO zif_customer.
lo_cust = NEW zcl_customer( ).
DATA(lv_name) = lo_cust->get_name( ).

Inheritance & Redefinition



CLASS zcl_base DEFINITION.
    PUBLIC SECTION.
        METHODS describe
            RETURNING VALUE(rv) TYPE string.
ENDCLASS.

CLASS zcl_child DEFINITION
    INHERITING FROM zcl_base.
    PUBLIC SECTION.
        METHODS describe REDEFINITION.
ENDCLASS.

Exception Classes

  • CX_STATIC_CHECK — must be declared or handled
  • CX_DYNAMIC_CHECK — checked at runtime
  • CX_NO_CHECK — not checked


" Declaring a static-check exception
METHODS do_work
    RAISING zcx_my_error.

" Raising it
RAISE EXCEPTION TYPE zcx_my_error
    EXPORTING
        textid = zcx_my_error=>invalid_input.
Exam focus: Understand what happens when an interface reference points to an implementing class and how method visibility and polymorphism work. Expect a question where a class implements two interfaces that both declare a method of the same name — you must know which one is called.

🎨 Design Patterns in ABAP

OO Design

Why Patterns Matter for the Exam

The exam does not ask you to write a pattern from scratch. It asks you to recognize which pattern solves a design problem, or to read code and identify the pattern in use.

Singleton

Intent

Ensure a class has exactly one instance and provide a global point of access to it. 



CLASS zcl_config DEFINITION.
    PUBLIC SECTION.
        CLASS-METHODS get_instance
            RETURNING VALUE(ro) TYPE REF TO zcl_config.
        METHODS get_value
            IMPORTING iv_key TYPE string
            RETURNING VALUE(rv) TYPE string.
    PRIVATE SECTION.
        CLASS-DATA go_instance TYPE REF TO zcl_config.
ENDCLASS.

CLASS zcl_config IMPLEMENTATION.
    METHOD get_instance.
        IF go_instance IS NOT BOUND.
            go_instance = NEW zcl_config( ).
        ENDIF.
        ro = go_instance.
    ENDMETHOD.
ENDCLASS.

Factory

Intent

Delegate object creation to a dedicated method or class so the caller does not depend on concrete classes. 



CLASS zcl_doc_factory DEFINITION.
    PUBLIC SECTION.
        CLASS-METHODS create
            IMPORTING iv_type TYPE string
            RETURNING VALUE(ro) TYPE REF TO zif_document.
ENDCLASS.

CLASS zcl_doc_factory IMPLEMENTATION.
    METHOD create.
        CASE iv_type.
            WHEN 'INVOICE'.
                ro = NEW zcl_invoice( ).
            WHEN 'ORDER'.
                ro = NEW zcl_order( ).
            WHEN OTHERS.
                RAISE EXCEPTION TYPE zcx_unknown_type.
        ENDCASE.
    ENDMETHOD.
ENDCLASS.

Strategy

Intent

Encapsulate interchangeable algorithms behind a common interface so they can be swapped at runtime. 



INTERFACE zif_pricing.
    METHODS calculate
        IMPORTING iv_amount TYPE decfloat34
        RETURNING VALUE(rv) TYPE decfloat34.
ENDINTERFACE.

CLASS zcl_tax_pricing  DEFINITION. " implements zif_pricing
CLASS zcl_discount_pricing DEFINITION. " implements zif_pricing

" Runtime selection
DATA lo_pricing TYPE REF TO zif_pricing.
IF lv_customer_type = 'VIP'.
    lo_pricing = NEW zcl_discount_pricing( ).
ELSE.
    lo_pricing = NEW zcl_tax_pricing( ).
ENDIF.
DATA(lv_total) = lo_pricing->calculate( lv_amount ).
How to spot them:
  • One instance + global accessor → Singleton
  • Creation behind a method returning an interface → Factory
  • Runtime swap of algorithm via interface reference → Strategy

🗄️ ABAP SQL & Code Pushdown

≤ 10%

Core Topics

  • SELECT / JOIN / WHERE
  • GROUP BY / HAVING / ORDER BY
  • Aggregations
  • SQL expressions & functions
  • Host variables (@)
  • Database-side processing
  • Code pushdown

Modern SELECT



SELECT FROM zcustomer
       FIELDS id,
              name,
              status
       WHERE status = @lv_status
       INTO TABLE @DATA(lt_customers).

Joins



SELECT FROM zcustomer AS c
    INNER JOIN zcompany AS co
        ON c~company_id = co~company_id
    FIELDS c~id,
           c~name,
           co~company_name
    WHERE c~status = @lv_status
    INTO TABLE @DATA(lt_result).

Aggregation & GROUP BY



SELECT FROM zorders
    FIELDS customer_id,
           COUNT(*) AS order_count,
           SUM( amount ) AS total_amount
    GROUP BY customer_id
    HAVING SUM( amount ) > @lv_min
    ORDER BY total_amount DESCENDING
    INTO TABLE @DATA(lt_totals).

SQL Expressions



" CASE, CAST, COALESCE, string functions
SELECT FROM zcustomer
    FIELDS id,
           name,
           CASE WHEN status = 'A'
                THEN 'Active'
                ELSE 'Inactive'
           END AS status_text,
           COALESCE( phone, 'N/A' ) AS phone
    INTO TABLE @DATA(lt_result).

Code Pushdown

Code pushdown means moving data-intensive processing as close to the database as appropriate instead of retrieving large datasets and processing everything in ABAP.

✓ Push down
  • Filtering (WHERE)
  • Joining related tables
  • Aggregation (SUM, COUNT)
  • Sorting (ORDER BY)
  • Column projection (only needed fields)
  • Calculations in SQL expressions
✗ Keep in ABAP
  • Complex procedural logic with side effects
  • Business rules requiring external calls
  • Row-by-row formatting for UI
  • Logic that cannot be expressed in SQL
Remember: Avoid unnecessary database round trips and unnecessary data transfer. Prefer appropriate SQL/CDS-based processing where possible.

🐞 Debugging & Performance

Core ABAP

Tools You Must Know

Tool Transaction Purpose
ABAP Debugger /h Step through running code, inspect variables
ABAP Profiler SAT Aggregated runtime analysis of ABAP execution
SQL Trace ST05 Analyze database access, find slow SQL
Code Inspector SCI Static checks: performance, security, syntax
ABAP Test Cockpit ATC Central quality gate for transports
Runtime Analysis SE30 Legacy predecessor of SAT

ABAP Profiler (SAT)

  • Aggregated view: total time per procedure
  • Hit list: most expensive operations
  • Call hierarchy: who called what
  • Database access breakdown

SQL Trace (ST05)

  • Captures all database statements during a trace
  • Identifies full table scans and missing indexes
  • Shows execution plan
  • Look for SELECT * where a narrower projection would suffice
  • Look for SELECT inside LOOP (classic performance killer)

Classic Anti-Patterns



" ❌ SELECT inside LOOP — N+1 queries
LOOP AT lt_customers INTO DATA(ls_c).
    SELECT SINGLE name FROM zcompany
        INTO @DATA(lv_name)
        WHERE company_id = @ls_c-company_id.
ENDLOOP.

" ✓ One JOIN or one SELECT ... FOR ALL ENTRIES
SELECT c~id, co~name
    FROM zcustomer AS c
    INNER JOIN zcompany AS co
        ON c~company_id = co~company_id
    INTO TABLE @DATA(lt_result).

Other Performance Principles

  • Select only the columns you need — avoid SELECT *.
  • Use WHERE, not ABAP filtering, when possible.
  • Use FOR ALL ENTRIES carefully — always guard against empty driver table.
  • Prefer ASSIGNING to INTO in loops for large rows.
  • Avoid nested loops when a hashed lookup works.
Exam trap: Given a slow report, the correct answer is almost always to reduce data transfer and push down processing — not to add buffering or increase memory.

📊 CDS Data Modeling

21–30%

CDS View Entity



@EndUserText.label: 'Customer'

define view entity ZI_Customer
    as select from zcustomer
{
    key id,
        name,
        status,
        created_by
}

Association



define view entity ZI_Customer
    as select from zcustomer

    association [0..1]
        to I_CompanyCode as _CompanyCode
        on $projection.CompanyCode =
           _CompanyCode.CompanyCode
{
    key id,
        CompanyCode,
        _CompanyCode
}

Cardinality



" [0..1]  = at most one
" [1..1]  = exactly one
" [0..*]  = any number
" [1..*]  = at least one

association [0..*]
    to I_OrderItem as _Items
    on $projection.OrderId = _Items.OrderId

Path Expression



_CompanyCode.CompanyName as CompanyName

Parameters



define view entity ZI_CustomerByStatus
    with parameters
        p_status : abap.char(1)
    as select from zcustomer
{
    key id,
        name,
        status
}
where status = $parameters.p_status

Things to Know Cold

  • Association vs JOIN — an association is a lazy, reusable relationship definition; a JOIN is eager and executed in the query.
  • Cardinality — declared on the association, used by consumers (e.g. RAP) to understand the relationship.
  • Path expression — navigate from one entity to another via _Association.Field.
  • Annotations — @EndUserText.label, @Semantics, @AccessControl, @ObjectModel — drive UI and behavior.
  • Parameters — input values bound at query time via $parameters.
Know: Understand the difference between associations, joins, cardinalities and path expressions. Expect a question where an association and a join produce the same result but only one is the "modeling" answer.

🔐 DCL / Authorization

Data Modeling

Basic DCL Concept

DCL defines authorization restrictions for CDS-based data access. 



@EndUserText.label: 'Customer Access'

define role ZI_Customer_Role {

    grant select on ZI_Customer

        where
            ( created_by = $user );

}

Important Concepts

  • DCL role
  • GRANT SELECT
  • $user / $session
  • Authorization conditions
  • CDS authorization annotations
  • Interaction between CDS and DCL
  • Access control on associations

How It Fits Together

Layer Controls
CDS view entity What data exists and how it is shaped
DCL role Who can read which rows
Authorization object Classic SAP authorization check
Behavior authorization (RAP) Who can create/update/delete
Exam trap: Know the difference between defining a CDS data model and restricting access to that data model. DCL is the authorization layer — it is not part of the view definition itself.

  • Draft

Managed vs Unmanaged

Managed
  • Framework handles CREATE/UPDATE/DELETE
  • Persistent table declared in BDEF
  • You add determinations, validations, actions
  • Default choice for new BOs
Unmanaged
  • You implement save/read logic yourself
  • Used when persistence is non-standard
  • Often wraps legacy APIs or external data
  • More code, more control
Think in layers: CDS describes the data. Behavior describes what can happen. Service definition describes what is exposed. Service binding makes that service available.

⚙️ RAP Behavior Definition

RAP

Managed Behavior



managed implementation in class
    zbp_i_customer unique;

strict ( 2 );

define behavior for ZI_Customer
persistent table zcustomer
lock master
authorization master
{
    create;
    update;
    delete;

    field ( readonly ) id;

    determination setStatus
        on modify { create; }

    validation checkName
        on save { create; update; }

    action approve result [1] $self;
}

Determination

Automatically derives or changes values based on business events. Triggered by framework events (on modify, on save).

Validation

Checks whether business data is valid before saving. Reports messages; does not change data.

Action

Represents an explicit business operation initiated by a consumer or application. Called via EML or OData.

Feature Control



" Static instance-level control
field ( readonly ) id, created_at, created_by;

" Dynamic via feature instance in implementation
" (e.g. disable delete for certain instances)
Very important: Do not confuse determination, validation and action.
  • Determination — derives/changes values
  • Validation — checks and reports
  • Action — explicit consumer-triggered operation

    REPORTED DATA(lt_reported).

EML Concepts to Know

  • READ ENTITIES / MODIFY ENTITIES
  • CREATE / UPDATE / DELETE
  • %cid — client-side temporary ID for new rows
  • MAPPED / FAILED / REPORTED
  • COMMIT ENTITIES
  • IN LOCAL MODE — bypasses authorization, used inside behavior implementations

EML vs ABAP SQL

Aspect EML ABAP SQL
Works on RAP business objects Database tables / CDS
Triggers behavior Yes (determinations, validations, actions) No
Authorization Yes (unless LOCAL MODE) Handled separately
Transactional buffer Yes — commit needed Direct DB write (in cloud, restricted)
Exam focus: Understand what EML is doing conceptually. Do not simply memorize one CREATE statement. Expect a question like: "You need to create a business object instance with all validations and determinations applied. Which mechanism?" Answer: EML, not direct SQL.

Why Clean Core?

The Clean Core approach aims to keep the SAP core stable and upgradeable while placing extensions in appropriate supported extension mechanisms.

Three Extension Models

Model Where Tools Use For
In-app Inside S/4HANA Cloud Key user tools, custom fields, custom logic Small config-level extensions by key users
Developer Inside S/4HANA Cloud ABAP Cloud, ADT, RAP, released APIs Full ABAP extensions, BAdIs, RAP BOs
Side-by-side SAP BTP ABAP environment ABAP Cloud on BTP New apps, integrations, extensions

Important Concepts

  • Released APIs (C0, C1 contracts)
  • Extension points
  • Upgrade stability
  • ABAP Cloud
  • Custom CDS entities
  • Released BAdIs
  • No modifications to SAP standard
Exam thinking: When several extension approaches are possible, consider whether the solution follows supported extension mechanisms and Clean Core principles. A modification to standard SAP code is almost never the right answer.

⚠️ C_ABAPD Exam Traps

Trap 1 — Classic ABAP ≠ ABAP Cloud

A statement or API that works in traditional ABAP does not automatically mean it is allowed in ABAP for Cloud Development.

Trap 2 — CDS ≠ RAP

CDS is used for data modeling and more. RAP builds transactional behavior and services around business objects.

Trap 3 — Determination ≠ Validation

A determination derives or changes values. A validation checks business consistency and reports messages.

Trap 4 — Service Definition ≠ Service Binding

The definition describes what is exposed. The binding connects the service to its runtime/protocol.

Trap 5 — Association ≠ Join

An association is a lazy, reusable relationship definition. A join is eager. Know why and when associations are used and how cardinality and path expressions work.

Trap 6 — Managed ≠ Unmanaged

Understand which parts of persistence and transactional processing are handled by the RAP framework and which parts require developer implementation.

Trap 7 — EML ≠ ABAP SQL

ABAP SQL works with database data. EML interacts with RAP business objects and triggers behavior.

Trap 8 — Static ≠ Instance Access

=> is for static members. -> is for instance members. A question may swap them.

Trap 9 — Standard ≠ Sorted ≠ Hashed

"Fastest by key" is hashed. "Fastest by index" is standard. Sorted sits in between and maintains order.

Trap 10 — Memorization Only

Do not prepare by memorizing code blocks. Be able to read a scenario and select the appropriate artifact or mechanism.

Trap 11 — Joule as a Shortcut

Joule assists but does not replace developer judgment. It cannot bypass cloud restrictions or guarantee Clean Core compliance.

🎬 Scenario-Based Practice Questions

SCENARIO 1. A business requirement states that when a new customer record is created, a default status of 'NEW' must be populated automatically before saving.

Which RAP mechanism should you use?

  • A. Validation
  • B. Determination
  • C. Action
  • D. Feature control
Answer: B — Determination A determination derives or populates values automatically on a framework event. A validation only checks and reports; an action is consumer- triggered; feature control toggles UI capabilities.

SCENARIO 2. A developer needs to create a business object instance from ABAP code so that all determinations, validations, and actions on the object execute.

Which mechanism should be used?

  • A. Direct INSERT into the persistent table
  • B. ABAP SQL INSERT
  • C. EML MODIFY ENTITIES ... CREATE
  • D. A CDS view entity
Answer: C — EML EML interacts with the RAP business object and triggers the framework's behavior pipeline. Direct SQL or INSERT bypasses behavior and is also restricted in ABAP Cloud.

MULTI SCENARIO 3. Which of the following are allowed in ABAP for Cloud Development? (Choose all that apply.)

  • A. Direct SELECT on a non-released transparent table
  • B. Calling a released RFC-enabled function module
  • C. Using a CDS view entity as a data source
  • D. Modifying SAP standard code via a modification assistant
  • E. Implementing a released BAdI
Answer: B, C, E Released RFC function modules, CDS view entities, and released BAdIs are all allowed. Direct SELECT on non-released tables is forbidden, and modifying SAP standard code is never Clean Core.

CODE 4. What is the correct syntax for calling a static method get_version of class zcl_util?

  • A. zcl_util->get_version( )
  • B. zcl_util=>get_version( )
  • C. zcl_util.get_version( )
  • D. zcl_util::get_version( )
Answer: B — => Static access always uses =>. The -> operator is only for instance members.

SCENARIO 5. A report reads a very large custom table (500,000+ rows) repeatedly by key inside a loop. The current implementation uses a STANDARD TABLE. What is the most appropriate change?

  • A. Add a secondary sorted key to the standard table
  • B. Change to a SORTED TABLE
  • C. Change to a HASHED TABLE
  • D. Add a database index
Answer: C — Hashed table If the table is always accessed by a unique key, a hashed table gives O(1) lookup. A sorted table gives O(log n); a standard table with WITH KEY is linear. A database index would not help an in-memory table.

SCENARIO 6. A business object needs a service that is consumed by a Fiori elements app. Which sequence is correct?

  • A. Service Binding → Service Definition → CDS
  • B. CDS → Behavior Definition → Service Definition → Service Binding
  • C. DCL → Behavior → Service Binding → CDS
  • D. CDS → DCL → Service Binding
Answer: B The data model (CDS) comes first, then the transactional behavior, then the service definition (what to expose), then the service binding (how to expose it).

CODE 7. In a behavior implementation, you see READ ENTITIES OF ZI_Order IN LOCAL MODE. What does IN LOCAL MODE do?

  • A. Reads from the database directly
  • B. Bypasses authorization checks
  • C. Forces draft handling
  • D. Uses the local ABAP memory
Answer: B — Bypasses authorization Inside behavior implementations, IN LOCAL MODE is used so that the framework-level authorization check is not performed again. The caller is already inside a controlled behavior context.

SCENARIO 8. A developer must restrict which rows of a CDS view entity a user can read based on their user name. Which artifact is used?

  • A. Behavior definition
  • B. Service binding
  • C. DCL role
  • D. ABAP Unit test class
Answer: C — DCL role DCL defines row-level access restrictions on CDS entities. Behavior definition handles transactional logic, not row-level read authorization.

SCENARIO 9. A report currently performs a SELECT inside a LOOP and the SQL Trace shows thousands of database calls. What is the best fix?

  • A. Add table buffering
  • B. Use a JOIN or FOR ALL ENTRIES to replace the SELECT-in-LOOP
  • C. Increase the application server memory
  • D. Change the internal table type to HASHED
Answer: B SELECT inside LOOP is a classic N+1 query problem. Replacing it with a single JOIN or FOR ALL ENTRIES read (guarded against an empty driver table) is the correct code-pushdown fix. Buffering does not fix the N+1 pattern.

SCENARIO 10. A customer wants to add a custom field and a small custom validation to a standard S/4HANA Cloud app without leaving the cloud environment. Which extension model fits best?

  • A. Classic modification via SMOD/CMOD
  • B. In-app extensibility with key-user tools
  • C. Side-by-side extension on BTP
  • D. Direct modification of SAP standard code
Answer: B — In-app extensibility For small, user-driven extensions inside S/4HANA Cloud, key-user in-app extensibility is the Clean Core choice. Modifications are never allowed; side-by-side is used for larger, decoupled apps.

🔬 Hands-On Lab: Build a Mini RAP App

Goal: Build a minimal RAP business object end-to-end in a BTP ABAP environment or the ABAP Developer Edition. Doing this once is worth more than reading ten explanations.

1 Create the persistent table

Create a transparent table ZCUSTOMER_LAB with fields: client, id (key), name, status, created_by, created_at.

2 Create a CDS view entity 



@AccessControl.authorizationCheck: #NOT_REQUIRED
@EndUserText.label: 'Customer Lab'

define view entity ZI_CustomerLab
    as select from zcustomer_lab
{
    key id,
        name,
        status,
        created_by,
        created_at
}

3 Create the behavior definition 



managed implementation in class
    zbp_i_customerlab unique;

strict ( 2 );

define behavior for ZI_CustomerLab
persistent table zcustomer_lab
lock master
authorization master ( instance )
{
    create;
    update;
    delete;

    field ( readonly ) id, created_by, created_at;

    determination setDefaults
        on modify { create; }

    validation checkName
        on save { create; update; }

    action approve result [1] $self;
}

4 Implement the behavior pool 



CLASS lhc_CustomerLab DEFINITION
    INHERITING FROM cl_abap_behavior_handler.

    PRIVATE SECTION.
        METHODS setDefaults FOR DETERMINE
            ON MODIFY IMPORTING keys FOR CustomerLab.

        METHODS checkName FOR VALIDATE
            ON SAVE IMPORTING keys FOR CustomerLab.

        METHODS approve FOR MODIFY
            IMPORTING keys FOR ACTION CustomerLab~approve
            RESULT result.
ENDCLASS.

CLASS lhc_CustomerLab IMPLEMENTATION.

    METHOD setDefaults.
        MODIFY ENTITIES OF ZI_CustomerLab IN LOCAL MODE
            ENTITY CustomerLab
            UPDATE FIELDS ( status created_by created_at )
            WITH VALUE #(
                FOR key IN keys (
                    %tky       = key-%tky
                    status     = 'NEW'
                    created_by = sy-uname
                    created_at = utclong_current( )
                )
            ).
    ENDMETHOD.

    METHOD checkName.
        READ ENTITIES OF ZI_CustomerLab IN LOCAL MODE
            ENTITY CustomerLab
            FIELDS ( name ) WITH VALUE #(
                FOR key IN keys ( %tky = key-%tky )
            )
            RESULT DATA(lt_cust).

        LOOP AT lt_cust INTO DATA(ls_cust).
            IF ls_cust-name IS INITIAL.
                APPEND VALUE #(
                    %tky = ls_cust-%tky
                ) TO failed-CustomerLab.

                APPEND VALUE #(
                    %tky = ls_cust-%tky
                    %msg = new_message_with_text(
                        severity = if_abap_behv_message=>severity-error
                        text     = 'Name must not be empty'
                    )
                ) TO reported-CustomerLab.
            ENDIF.
        ENDLOOP.
    ENDMETHOD.

    METHOD approve.
        MODIFY ENTITIES OF ZI_CustomerLab IN LOCAL MODE
            ENTITY CustomerLab
            UPDATE FIELDS ( status )
            WITH VALUE #(
                FOR key IN keys (
                    %tky   = key-%tky
                    status = 'APPROVED'
                )
            ).

        READ ENTITIES OF ZI_CustomerLab IN LOCAL MODE
            ENTITY CustomerLab
            ALL FIELDS WITH VALUE #(
                FOR key IN keys ( %tky = key-%tky )
            )
            RESULT DATA(lt_result).

        result = VALUE #(
            FOR ls IN lt_result (
                %tky   = ls-%tky
                %param = ls
            )
        ).
    ENDMETHOD.

ENDCLASS.

5 Create the service definition 



@EndUserText.label: 'Customer Lab Service'

define service ZUI_CUSTOMERLAB {
    expose ZI_CustomerLab as CustomerLab;
}

Create a service binding for ZUI_CUSTOMERLAB with type OData V4 — UI. Activate and use the preview to test your service.
